# An execution profile pins the platform, not the toolchain

A CI receipt is only evidence if a reader can tell what environment produced it, so an **Execution Profile** must record the facts a repository cannot state about itself: operating system, architecture, and machine class. It deliberately does **not** record the resolved toolchain — the `rustc`, `cargo`, `node`, or `pnpm` a target happens to have installed. Those are already commit-bound by repository-owned files (`rust-toolchain.toml`, `packageManager`) that travel with the exact revision a **Job** pins, so recording them again on the target would duplicate a fact the commit already carries while making the target the authority on tools CommonKit does not manage. Rejected for that reason: having targets introspect and hash installed tool versions into `executionProfileDigest`, which would additionally invalidate every declared manifest on any routine version bump until each was re-registered, turning a patch upgrade into a fleet-wide placement outage. Also rejected: materializing toolchains through a **Loadout**, which would make CommonKit a package installer and contradict the boundary that gives package resolution to the selected **Agent-context provider**. The consequence accepted is that loadout-digest equality proves CommonKit-managed environment equality and not compiler equality — a repository that pins nothing gets a receipt that is honest about the platform and silent about its tools, which is a repository problem the evidence model should not paper over. This follows the existing `BrowserProfile` precedent, which pins Chromium revision, operating system, fonts digest, locale, timezone, and viewport, and rejects mismatched environments as incomparable rather than quietly comparing them.
