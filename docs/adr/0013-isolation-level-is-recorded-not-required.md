# Isolation level is recorded evidence, not an admission requirement

A macOS **Execution Target** cannot provide what a Linux one does: `SystemdScope` gives cgroup CPU and memory ceilings wrapped around a bubblewrap sandbox with namespace, mount, and network isolation, while macOS realistically offers a process group with a timeout, an `RLIMIT_FSIZE` cap, and polled disk growth, and Windows additionally cannot reliably terminate a process tree because cancellation kills the child rather than a Job Object. We ship those workers anyway and record the isolation level each target actually provided as part of its **Execution Profile**, so a receipt states the boundary its result was produced under and placement refuses to treat two isolation levels as interchangeable. Rejected: withholding macOS and Windows workers until parity, which is the posture CommonKit already takes for *external provider* execution on macOS — but that posture protects against checksum-pinned third-party binaries with detached descendants, whereas a **Declared task** is the repository's own committed check, reviewed in its own tree, running against a revision the manifest pins. Holding the stronger rule here would leave precisely the support-matrix rows that are emptiest empty forever, trading real evidence for a guarantee that was never the threat model. Also rejected: admitting weak isolation silently, which would let a macOS pass and a Linux pass look identical in a receipt when they are not comparable. The consequence accepted is that "passed" means less on some platforms than others, and the profile is what says so — which is the same discipline `BrowserProfile` already applies by declaring mismatched environments incomparable rather than quietly comparing them. Windows is the sharper case and fails closed on one point regardless: its secret-file permission validation does not exist, so a Windows worker must refuse a secrets file until ACL checking is implemented rather than load one it cannot vouch for.
