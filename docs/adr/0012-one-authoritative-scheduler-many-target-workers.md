# One authoritative scheduler, many target-resident workers

Per-platform **Validation evidence** requires macOS and Windows **Execution Targets**, so durable execution grows from one worker to several — by adding worker identities to a single authoritative scheduler, not by running a scheduler per machine and federating across them. The scheduler is already built for this: `targets.id` is a primary key carrying its own worker ID, capabilities, and heartbeat, and `acquire` transitions only a still-queued attempt inside an `IMMEDIATE` transaction, so distinct workers lease distinct jobs without coordination. What is genuinely single-worker is the process: `commonkit-execd` binds exactly one worker token to exactly one worker ID and couples the API and the worker in one binary, with the worker reaching the scheduler in-process rather than over HTTP. Growing therefore means per-target worker tokens, a worker-only mode, and completing the remote worker data plane — the authenticated worker API today offers lease, renew, checkpoint, complete, and heartbeat but no state transitions and no artifact upload, which an off-box worker needs. Rejected: one scheduler per machine with a federating client, which would require inventing cross-scheduler identity, idempotency, cancellation, and evidence semantics, and would fragment the authoritative placement and receipt story that makes evidence trustworthy. The single SQLite writer stays a deliberate limit rather than an accident: it is correct for a handful of targets and is not high availability, and CONTEXT.md's one-authoritative-writer-per-database rule holds unchanged. "Run this on every platform" is expressed as one **Declared task** per platform, each capability-labelled, rather than as matrix or fan-out semantics in the scheduler — immutable manifests make three explicit declarations honest and need no new machinery.
